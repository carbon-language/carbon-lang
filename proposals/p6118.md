## Abstract

Carbon's language goals include support for
[practical safety mechanisms](/docs/project/goals.md#practical-safety-and-testing-mechanisms).
The [updated](p5914.md) Carbon safety strategy clarifies this by including the
requirement of using Carbon as a "rigorously memory safe programming language".

This proposal introduces a principle "flow checking" to clarify, at a high
level, a technical approach to memory safety through static checking.

## Problem

A programming language design can support static checking and safety properties
in many different ways. How such checking is related to type-checking is one
particular, fundamental design question. By clarifying the high-level approach
taken, this proposal clarifies the direction, identifies open questions and
enable more concrete discussion.

## Background

Carbon's safety model needs to support both temporal memory safety and
fine-grained control over memory, in a way that supports high performance
scenarios. This is known to be a very hard problem.

A general direction is to make language design and conforming compilers
infer static properties and prevent safety bugs. This requires annotation by
programmers that clarify intent and enough basic information so that static
analysis can capture precise enough information to analyze interesting
programming scenario. In Carbon, every program statement can potentially lead to
updates to the program state, which needs to be approximated in static analysis.

This naturally leads to the question how safety annotations and information
about statically approximated flow state should relate to the type system or
not. A traditional type system tracks invariants about data and usually an
identifier keeps the same type throughout its scope. The choice is then to
change this and depart from usual type systems, or to find an alternative way
that preserves the role of a traditional type system and does safety-related
checking differently.

## Proposal

Flow checking is a specific form of static checking that is defined by the
following characteristics:

-   flow- and path-sensitivity: flow checking ensures properties that hold at
    every program point, taking into account information available from
    instructions and certain branch conditions leading up
-   hybrid: flow checking is layered over a core, flow-insensitive type system
    as a "conservative extension". Code must be accepted by the type system to
    be considered for flow checking, and information obtained through flow
    checking does not influence type system.
-   can optionally rely on annotations to specify effects of operations. This
    information can be used to identify operations which may cause bugs, even if
    they look acceptable from a type checking point of view.

This definition is intentionally abstract and leaves out constraints on the type
systems. A core type system statically checks which operations are permitted on
data. This gives possibility of enforcing a programming discipline that
maintains global invariants, which in turn can be useful for memory safety and
flow checking.

Rust borrow checking is one form of flow checking system that relies heavily on
type invariants ("aliasing-xor-mutability"). Rust does not need effect
annotations because the type invariants are very strong and generic library
types that provide functionality provide sound operations where the strength of
the invariants hurt expressivity.

Carbon's system of flow checking may choose less strong type invariants and/or
different core library operations to enable sound memory safe programming
patterns. In particular, it is possible to come up with more permissive regime
for control of aliasing and non-interference.

## Details

Temporal memory safety is about ensuring _reference validity_ in

Carbon reference expressions correspond to memory locations (references).
Through references, memory can be read and written to, which changes object
graph. Operations like destruction or reallocation can render references
invalid. Preventing access through invalid references requires keeping track of
changes to the object graph. This is known to be very difficult in the presence
of aliasing.

Doing this precisely is not possible for decidability reasons, therefore static
checking has to work with approximations.

A standalone flow-insensitive type discipline that aims to provide safety has to
satisfy the following statement (type soundness):

> If (program is well-typed) then (program execution is well-behaved)

Type-checking enforces a type-discipline, restricting what programmers can do.
In return, programmers can be certain that certain errors are diagnosed. The class of errors
prevented depends on the kind of properties that are captured in the type system.

Expressive type systems can capture many interesting properties, but there are
also always well-behaved programs which may not pass type checking.

Type safety in languages like C++ has come to mean preventing type errors due to
mismatching between data and supported operations. This is not enough for memory
safety and sound execution. Carbon's goal of incremental migration from C++
means that type-checking has to be close in spirit to C++: idiomatic C++ code
may use programming patterns that are too difficult to recognize as
well-behaved.

Rather than overloading the requirements on the type system with two conflicting
goals, familiarity with C++ and rigorous memory safety, there is an alternative
of pursuing these in two separate systems:

> If (program is well-typed) then (if (program is flow-checked) then (program
> execution is well-behaved))

This split enables Carbon's permissive mode to have a notion of type-checking
which is close enough to C++ to enable straightforward migration while at the
same time ensuring that strict Carbon programs can be rigorously verified to be
memory safe.

## Rationale

This proposal advances Carbon's goals by constraining Carbon's safety model to
evolve without drastic changes to type checking.

-   [Practical safety and testing mechanisms](/docs/project/goals.md#practical-safety-and-testing-mechanisms)
-   [Interoperability with and migration from existing C++ code](/docs/project/goals.md#interoperability-with-and-migration-from-existing-c-code)

## Alternatives considered

Rust type-and-borrow-checking can be considered a flow checking system. Rust's
safety model is built on strong type invariants. These invariants make migration
from C++ very difficult, but here the point is on the architecture. Borrow
checking operates on MIR where all decisions regarding temporaries and
control-flow have been made explicit. Borrow checking takes liveness of
variables into account. So while committing to strong type invariants upfront is
an alternative to flow checking, the architecture of doing flow checking after
type checking is very similar.

Flow checking as a principle is compatible with adding information to types.

Doing a traditional static analysis without any annotations with the goal of
detecting memory access bugs is not interesting as an alternative: it has been
explored in the context of C and C++ for decades for bug finding tools. Even
adding when annotations are added, it has not been possible to make significant
safety guarantees.
