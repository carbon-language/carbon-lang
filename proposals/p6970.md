## Abstract

Allow a Carbon library to be able to provide logging facilities in a way that
are zero overhead when disabled at compile time. We address this by providing
syntactic sugar for lazy evaluation of function arguments.

## Problem

Carbon needs a migration story for logging. In C++, logging is commonly done
through macros, which provides the following properties:

-   When disabled at compile time, the LOG statement is completely compiled
    away. This includes any conditions within, and any arguments for printing.
    It has no side effects.
-   When disabled at compile time, variables that are named in the LOG
    statement, in a condition or for printing, are still marked as "used" and
    thus prevent "unused variable" warnings from appearing based on the
    compilation mode.
-   May be enabled/disabled at runtime.
-   Have multiple levels, or severities, and then allow disabling by severity at
    compile time or runtime. For example `DEBUG`, `INFO`, `ERROR`.
-   Can be provided a condition, and conditionally log the arguments for
    printing if it passes.
-   Have one or more "verbose" levels, which can be disabled at compile time, or
    conditionally enabled at runtime based on user interest.
-   Allow C++ streaming operators to be used for providing arguments for
    printing. Though more modern libraries may use a format string with variadic
    arguments instead.
-   Maintain the source location of the caller, so logging can observe where the
    log message was written (through `__FILE__` and `__LINE__`). Modern C++ can
    use `std::source_location` with a default argument value to provide a
    similar experience.

In the C++ dialect without exceptions, these same facilities are sometimes used
for checking runtime conditions. Logging is easily extended to support a `FATAL`
log level, which can then be reframed as a `CHECK` when provided a condition.

This proposal covers the ability to compile away code under certain build modes.

## Background

-   Some examples of C++ logging libraries:
    -   [Abseil log library](https://abseil.io/docs/cpp/guides/logging)
        -   Provides macros such as `LOG`, `LOG_IF`, `CHECK`, `LOG_EVERY_N`.
        -   Has modifiers that present as methods of the macro.
        -   Built on C++ stream operators.
    -   [Chromium log library](https://source.chromium.org/chromium/chromium/src/+/main:base/logging.h)
        -   Provides macros such as `LOG`, `LOG_IF`, `CHECK`, `DCHECK`.
        -   Built on C++ stream operators.
    -   [fmtlog library](https://github.com/MengRao/fmtlog)
        -   Provides macros such as `logd`, `logi`, `loge`.
        -   Built on [fmtlib](https://github.com/fmtlib/fmt) format strings.

Widely used Rust logging library:

-   [log crate](https://docs.rs/log/latest/log/)
    -   Provides macros such as `log!`, `info!`, `error!`.
    -   Built on format strings.

Lazy evaluation: https://wiki.haskell.org/Lazy_evaluation

# Lazy evaluation

`DCHECK!(condition) <<! "start <<! GetMoreStuff();`

> Forms can differ in an impl from the interface:
>
> I think what we said last time we thought about this was:
>
> -   If the call site is symbolically selecting the callee, then we're calling
>     through the thunk. So the signature in the interface is what we call, and
>     that will internally forward to the signature in the impl. (And the impl
>     is invalid if it can't.)
> -   If the call site is concretely selecting the callee, then we effectively
>     produce a callee that implements the call interface in two ways
>     (interface + impl). We'll pick the better impl of the call interface given
>     the arguments, and if that's the one in the impl, you get to use the extra
>     properties from the impl function.
>
> While that was about the case where the parameter types or forms were
> different, maybe the same thing applies here

The thunk would either apply laziness or undo it depending on what the concrete
callee wants.

I think that gives us a path for no compiler errors, but the downside is the
laziness would feel very non-deterministic. Refactoring code could change
execution behaviour a ton but introducing a thunk.

That might not matter in practice for us here. LOG() is always going to return a
concrete value.

So maybe we could say ! requires a concrete impl for now, and we make an error
at the ! call to an interface if it can't find one, rather than causing a
monomorphization later. That's at least deterministic. And if you're using fn!
that might be the right tradeoff?

Maybe... `I.F!()` on an interface `I` requires either:

-   The interface fn `F` is declared `fn!`. Then all impls must also be `fn!`.
-   Impl lookup finds a final witness that has `F` declared `fn!`.

-   Swift did this, sort of. They have call-by-name by way of @auto_closure
    https://www.russbishop.net/swift-call-by-name
