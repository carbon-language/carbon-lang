## Abstract

Extend the orphan rule to require that at least one name in the type structure
of an `impl` declaration is defined in, or by, the same scope as the `impl`
declaration, or in a scope nested within the scope of the `impl` declaration.

## Problem

The current orphan rule states:

> Some name from the type structure of an `impl` declaration must be defined in
> the same library as the `impl`, that is some name must be _local_.

This allows an out-of-line `impl` declaration in generic scope without any
reference to the generic bindings. In the following example, the impl has a
generic binding `T`, inherited from its enclosing scope. But it has no way to
provide a value for `T` since all names in its type structure come from outside
the generic scope, and thus can have no reference to the binding `T`.

```carbon
interface Z {}
class C;
fn F(T:! type) {
  impl C as Z;
}
```

This also allows an `impl` to be declared in a scope that is closed, but that
should be found and modify behaviour outside the scope, since it contains only
names that exist outside its current scope.

```carbon
interface Z {}
class C;
fn F() {
  impl C as Z;
}
fn G() {
  // This would need to find an `impl` in a scope that is no longer accessible.
  C as Z;
}
```

We want to preserve the limitations of the current orphan rule, but extend it to
limit `impl` declarations like the above so that it will require a relationship
to the generic binding `T`.

## Proposal

We propose to extend the orphan rule to:

> Some name from the type structure of an `impl` declaration must be defined
> within, or by, the same scope as the `impl` declaration. A name defined in a
> nested scope is considered defined within its enclosing scopes. That is, some
> name must go out of scope with or before the `impl` declaration, so that the
> `impl` declaration only needs to be considered when its scope is visible,
> through nesting or by import.

## Details

This proposal subsumes the existing orphan rule. Libraries can not be nested
within each other, so an `impl` declaration must still refer to some name in its
current library. But it also further restricts which `impl` declarations can be
written, so that they do not refer only to names defined outside their current
scope.

All examples below assume the "z" library is available as follows, and imported:

```carbon
library "z";
interface Z {}
```

There are three cases allowed by the new rule:

1. A name is defined in the same scope as the `impl` declaration.

```carbon
fn F() {
  class C {}
  impl C as Z;
}
```

Here the `impl` declaration is in the scope of `fn F`, and `C` is defined within
the same scope. When the function `F` closes, the name `C` is no longer
accessible, so the `impl` declaration no longer needs to be considered.

2. A name is defined by the same scope as the `impl` declaration.

```carbon
fn F() {
  class C {
    impl Self as Z;
  }
}
```

Here the `impl` declaration is in the scope of `class C`, and `C` is defined by
the same scope. The name `C` is accessible in the enclosing scope, so the `impl`
declaration must be considered. But when the enclosing scope is not accessible,
making `C` inaccessible, and the `impl` declaration does not need to be
considered.

3. A name is defined in a scope nested within the scope containing the `impl`
   declaration.

```carbon
fn F() {
  class C {
    class D {}
  }
  impl C.D as Z;
}
```

Here the `impl` declaration is in the same scope as `class C`, and `class D` is
defined within the nested scope of `class C`. The name `D` is accessible through
the name `C`, so the `impl` declaration needs to be considered as lone as `C` is
accessible. Thus we can fall back to the second case here, for the first scope
in the name `C.D`, which is `C`.

### Re-entering a nested scope in an `impl` declaration

It is possible to re-enter a nested scope by writing a qualified path for the
entire `Type as Interface` expression, such as `impl C.(D as Z)`. This functions
like writing `impl D as Z` within the nested scope `C`, or in other words, by
performing name lookups from the scope of `C`.

By re-entering the nested scope `C`, the rule becomes that the `impl`
declaration must name something defined within, or by, the re-entered scope `C`.

For example, this is equivalent to writing `impl C.D as Z`, which is allowed by
the proposed orphan rule.

```carbon
class C {
  class D {}
}
impl C.(D as Z);
```

Whereas while it is possible to write `impl C as Z` at the top level, or within
`C`, it is not allowed to write `impl C as Z` inside the scope of `D`, so it is
also not allowed to write `impl C.D.(C as Z)`.

```carbon
class C {
  class D {}
}
// ERROR: Neither C nor Z is defined within, or by, the scope `C.D`.
impl C.D.(C as Z);
```

### Interaction with evaluation

The orphan rule is applied to the impl declaration after evaluation. This means
aliases and compile-time functions are evaluated and resolved before the rule is
verified.

The following is an rejected, since neither `C` and `Z` are defined within, or
by, the same scope as the `impl` declaration.

```carbon
library "a";

musteval fn F() -> auto {
  class C {}
  return C;
}
```

```carbon
library "b";
import library "a";

musteval fn G() -> auto {
  return F();
}

// ERROR: Neither C nor Z is defined within, or by, the scope current scope.
impl G() as Z;
```

But if the `class C` is defined in a function that is within the same scope as
the `impl` declaration, then it is accepted.

```carbon
musteval fn G() -> auto {
  class C {}
  return C;
}

impl G() as Z;
```

## Rationale

This resolves an issue where an `impl` can be declared but impossible to use,
since there's no way to specify a value for its generic bindings. Clearly
rejecting code that is invalid follows the principle of
[Code that is easy to read, understand, and write](/docs/project/goals.md#code-that-is-easy-to-read-understand-and-write).

## Alternatives considered

### A syntactic check, instead of applying the rule after evaluation

This avoids the need to look "through" a function to figure out where a given
entity was defined. But creates other questions instead. It would prevent the
use of evaluation in an `impl` declaration, which would prevent things like
aliases as well, and would generally be fighting against Carbon's eager
evaluation model.
