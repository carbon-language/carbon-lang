## Abstract

We propose:

-   Special types `Core.ParamForm`, `Core.ReturnForm`, and `Core.CommonForm`
    that describe the form (category, phase, and so on) of parameters or returns
    in the signature of functions.
-   A `form(`...`)` literal syntax for writing values of these form types.
-   Constraints on form types may be composed using `&`, like for example to
    support `AddWith` doesn't allow `ref` parameters.
-   `:?` binding and `->?` return syntax parameterized by a form value.
-   Form versions of interfaces, facets, and facet types.
-   Use these special types to add support for different parameter and return
    forms to create new "primitive" versions of the operator interfaces, like
    `Core.CallPrimitive`.
-   A `call(`...`)` syntax for concisely and naturally writing facet types of
    the `Core.CallPrimitive` interface.
-   Impl lookup will allow some conversions between `ParamForm` values in
    interface arguments.
    -   FIXME: `anchor` instead of `like`
-   FIXME: associated constants of named constraints

Together these changes will allow:

-   the operator interfaces to support Carbon's full range of function
    semantics, particularly in the `Core.CallPrimitive` form interface;
-   defining convenience named constraints like `Core.Call` and `Core.AddWidth`
    that use types instead of forms;
-   full-fidelity forwarding of function parameters; and
-   a syntax for a compile-time parameter that is equal to a specified value.

## Problem

The `Core.Call` interface defined in
[proposal #2875](https://github.com/carbon-language/carbon-lang/pull/2875) does
not support all of the features of function calls:

-   `var` and `ref` parameters;
-   `bound` parameters;
-   mutation of the callable object using `ref self`;
-   compile-time parameters, as designated by `:!` or `template`...`:!`; and
-   compile-time parameters that are mentioned elsewhere in the signature.

In addition, we want to be able to express these aspects of parameters in other
contexts:

-   Some interfaces, such as operators, should support `impl`s specifying these
    aspects for the parameters of the interface's member functions. For example,
    a type should be able to implement `Core.AddWith` in a way that uses `var`
    or compile-time parameters, but not `ref`.
-   We would like there to be a way to forward arguments passed to one function
    to another function it calls, preserving those aspects. For example, there
    should be a way to write
    [`Apply`](https://en.wikipedia.org/wiki/Function_application) that takes a
    function and arguments to call it with and performs the call (so
    `Apply(F, x)` returns `F(x)`).

Ideally, our call operator interface would support:

-   **Uniformity**: ("consistent and universal") Ordinary functions, lambdas,
    and bound methods are all values of types that implement the call operator
    interface with the relevant signature. This is to enable a single constraint
    on a parameter to accept any of these. This also implies that implementing
    the call operator interface is sufficient to express the full range of
    function signatures, including `var` and `ref` parameters.
-   **Functors**: Types may implement the interface to be callable using the
    normal function-calling syntax, like implementing `operator()` in C++. A
    closure is syntactic sugar for declaring and creating a value of such a
    type.
-   **Overloading**: There is a relatively convenient way to define a function
    value whose type has multiple implementations of the "call operator"
    interface.
-   **Dispatch**: There is a method of matching actual call invocations to
    implementations of the "call operator." It should be as similar as possible
    to other cases of `impl` selection, including supporting the same
    `match_first` `impl` prioritization system (or whatever we replace that
    with). However, it also needs to be able to support the expected implicit
    conversions from the arguments values to the parameter types.
-   **Subsumption**: An overload set containing two functions, one accepting a
    `bool` and one accepting an `i32`, should be able to be passed as an
    argument to a function requiring a callable accepting a `bool`. This same
    mechanism should allow a generic function with signature that could accept a
    `bool`, such as `fn F[T:! type](x: T)`, to be passed to the function
    requiring a callable accepting a `bool`, using the instantiation with
    `T == bool`.
-   **Closed**: There is a way to say "just these implementations and no
    others." This should be the default when defining function overloads.

However, fully addressing the last four of these properties is out of scope of
this proposal, since it won't address declaring overloaded functions and `impl`
prioritization. We still would like the decisions in this proposal to be
consistent with a future solution that achieves those properties.

## Proposal

### Form types and values

First, we introduce three new special types that describe the form of bindings
and returns:

-   `Core.ParamForm` describes the form of a pattern, such as a function
    parameter or `let` binding. FIXME: QUESTION: could be `PatternForm` instead,
    which do we prefer? "Param" conveys the variance and common use case, but
    "Pattern" makes it clearer it could be in a `let x:? PF = ...`.
-   `Core.ReturnForm` describes the form of a function return and the form of an
    expression.
-   `Core.CommonForm` describes a form used in both contexts, and so is
    restricted to `let` and `ref` forms.

Values of these form types are compile-time only, like types.

-   `Core.ParamForm` and `Core.CommonForm` values can be used to customize
    parameters in the signature of functions, using a new `:?` binding syntax,
    which is also usable in `let` declarations in a function body.
-   `Core.ReturnForm` and `Core.CommonForm` values can be used to customize the
    return form of a function, using a new `->?` return syntax, either as the
    whole return form or as a member of a paren or brace form.

Forms can be compound forms or atomic forms. A paren compound form is
represented by the sequence of forms of its elements. A brace compound form is
represented by the sequence of names and forms of its members. Atomic forms have
different representations based on their type.

#### `Core.ParamForm`

A `Core.ParamForm` represents everything about a binding except the name being
bound. An atomic `Core.ParamForm` has:

-   a type
-   the category of the binding, which can be `Value`, `Ref`, or `VarParam`
-   whether the binding is marked with `bound`
-   the phase, which can be "compile time" or "execute time"
-   for compile time phase, the specific compile time value matched

An atomic `ParamForm` value with "execute time" phase can be written
`form(`_cat_`_:`_type_`)`, where _cat_ is an optional category modifier, and
_type_ is a type expression:

| `form` syntax    | category   |
| :--------------- | :--------- |
| `form(_: T)`     | `Value`    |
| `form(ref _: T)` | `Ref`      |
| `form(var _: T)` | `VarParam` |

An atomic `ParamForm` value with "compile time" phase is written `form(N)` where
`N` is an expression with compile-time phase. The category of `form(N)` matches
the category of the expression `N`.

| `form` syntax | phase         |
| :------------ | :------------ |
| `form(_: T)`  | `ExecuteTime` |
| `form(N)`     | `CompileTime` |

#### `Core.ReturnForm`

A `Core.ReturnForm` represents everything about the return of a function. An
atomic `Core.ReturnForm` has a type and a category from `Value`, `Ref`, and
`InitReturn`. They always have "execute time" phase. An atomic `ReturnForm`
value can be written `form(-> `_cat_ _type_`)`, where _cat_ is an optional
category modifier and _type_ is a type expression:

| `form` syntax    | category     |
| :--------------- | :----------- |
| `form(-> let T)` | `Value`      |
| `form(-> ref T)` | `Ref`        |
| `form(-> T)`     | `InitReturn` |

#### `Core.CommonForm`

A `CommonForm` atomic form has a types and a category that is either `Value` or
`Ref`. They always have "execute time" phase. An atomic `CommonForm` value can
be written `form(`_cat_ _type_`)` where _cat_ is a required category keyword and
_type_ is a type expression.

| `form` syntax | category |
| :------------ | :------- |
| `form(let T)` | `Value`  |
| `form(ref T)` | `Ref`    |

#### Compound form value literals

A compound paren form is written `form((`...`))`, where the `...` is a
comma-separated list of form literals written without the `form(`...`)` on the
outside. For example, `form((_: T, var _: U))` is a parameter paren form and
`form((-> let T, -> var U))` is a return paren form.

A compound brace form is written `form({`...`})`, such that the `{`...`}`
matches a brace pattern form or brace return form. So a brace parameter form is
written like `form({.a = _: T, .b = ref _: U})` or equivalently
`form({a: T, ref b: U})`. A brace return form is written like
`form({-> let .a: T, -> var .b: U})`.

FIXME: QUESTION: does a return form have to start with `->` so these should be
replaced by `form(->(-> let T, -> var U))` and
`form(->{-> let .a: T, -> var .b: U})`?

The compound forms can be nested:

-   `form({.a = (_: T, var _: U), .b = ref _: V})`, or equivalently
    `form({a: (_: T, var _: U), ref b: V})`, shows nesting parens inside braces
    in a param form.
-   `form({.a: (-> T, -> var U), -> ref .b: V})` shows the same thing in a
    return form.

It is invalid to mix param and return forms in a compound form. You can mix
param and common or return and common, getting a param form or return form
respectively. A compound form with only common forms is a common form.

| `form` example               | type         |
| :--------------------------- | :----------- |
| `form((let T, ref U))`       | `CommonForm` |
| `form((let _: T, ref _: U))` | `ParamForm`  |
| `form((let _: T, ref U))`    | `ParamForm`  |
| `form((-> let T, -> ref U))` | `ReturnForm` |
| `form((let T, -> ref U))`    | `ReturnForm` |
| `form((let _: T, -> ref U))` | ❌ Invalid   |

### Form facet types

_Form facet types_ are our way of expressing a form type with some additional
restrictions. The values of form facet type are _form facets_, which are values
that are implicitly convertible to the corresponding form type. For example, the
operator interfaces for many operators, such as `+`, don't want to allow `ref`
parameters, and so could use `Core.NoRefParam` to get a `Core.ParamForm` facet
type with that restriction. A value of `Core.NoRefParam`, like
`form(_: i32) as Core.NoRefParam`, is implicitly convertible to
`Core.ParamForm`, resulting in `form(_: i32)`. Here are some form facet types of
the different form types:

-   `Core.ParamForm` facet types: `Core.NoValueParam`, `Core.NoRefParam`,
    `Core.NoVarParam`, `Core.NoCompileTimeParam`, `Core.NoExecuteTimeParam`,
    `Core.NoBoundParam`
-   `Core.ReturnForm` facet types: `Core.NoValueReturn`, `Core.NoRefReturn`,
    `Core.NoInitReturn`
-   `Core.CommonForm` facet types: `Core.NoValueCommon`, `Core.NoRefCommon`

Use `&` to combine form facet types of the same kind to get one that requires
its values to satisfy the constraints from both, as in
`Core.NoRefParam & Core.NoCompileTimeParam` to say a parameter form that doesn't
use `ref` or compile-time forms.

### Specifying the form of a binding

The `n :? B` binding syntax creates a binding to the name `n` with form given by
`B`. Note that `B` will be implicitly converted to `Core.ParamForm`, much like a
`:` binding will implicitly convert its right-hand argument to `type`. Example:

```carbon
fn VarFn(x:? form(var _: i32));
// is equivalent to:
fn VarFn(var x: i32);

// `CommonForm` values such as `form(ref i32)`
// implicitly convert to `ParamForm`, so:
fn RefFn(x:? form(ref i32));
// is equivalent to:
fn RefFn(x:? form(ref i32) as Core.ParamForm);
// is equivalent to:
fn RefFn(x:? form(ref _: i32));
// is equivalent to:
fn RefFn(ref x: i32);
```

While this is valid, this is not how this feature is expected to be used.
Instead, the form value will typically be a generic parameter.

```carbon
fn Explicit(PF:! Core.ParamForm, arg:? PF);

//  ✅ Valid since 5 can be passed to a
// `var _: i32` parameter.
Explicit(form(var _: i32), 5);

// ❌ Invalid, `5` is not a reference
// expression.
Explicit(form(ref _: i32), 5);

// ❌ Invalid, `true` can't be cast to `f32`.
Explicit(form(_: f32), true);
```

A `Core.ParamForm` or `Core.CommonForm` parameter is deducible from an argument
expression, allowing it to capture the argument's expression category, phase,
and compile-time value (but not whether it is `bound`).

```carbon
fn Deduced[PF:! Core.ParamForm](arg:? PF);

let l: bool = true;
// Deduces PF = form(_: bool).
Deduced(l);

var v: i32 = 4;
// Deduces PF = form(var _: i32).
Deduced(v);

// Deduces PF = form(7).
Deduced(7);
```

### Specifying the form of a return

The `->? R` return syntax specifies a return with form `R`. The `R` will be
implicitly converted to `Core.ReturnForm`, much like the expression to the right
of `->` will be implicitly converted to `type`.

### Form type conversions

We define conversions between the form types. This is to support use cases where
we need a form in two different positions. Examples:

-   The form describes a parameter that is to be returned.
-   The form describes a return that will be used as an argument.
-   The form is an interface parameter used in a number of function signatures
    within the interface.

Note that the `CommonForm` _implicitly_ converts to the other form types. Its
values are naturally included since `CommonForm` represents the intersection of
`ParamForm` and `ReturnForm`. The other conversions are explicit.

These conversions follow these rules:

-   Conversion to `CommonForm` maps `Ref` -> `Ref`, and anything else to
    `Value`.
-   Conversion from `ReturnForm` to `ParamForm` maps `InitReturn` to `VarParam`.
    This is used to when deducing a parameter form from an argument expression.
-   Conversion from `ParamForm` to `ReturnFrom` maps `VarParam` to `InitReturn`.
    Would be used in this example:

    ```carbon
    interface Callback(PF:! ParamForm) {
      fn Call(x:? PF);
      fn DefaultArgument() ->? (PF as ReturnForm);
      final fn CallWithDefault() {
        Call(DefaultArgument());
      }
    }
    ```

-   Conversion to a `ParamForm` always uses "execute time" phase and is never
    `bound`. The exception is an argument expression with compile-time phase can
    be used to deduce a compile time `ParamForm`. Broader support for
    compile-time phase is [future work](#compile-time-calls).
-   Conversion of a compile-time phase `ParamForm` value to a `CommonForm` or
    `ReturnForm` is an error (similar to the conversion error `256 as i8`).
-   Conversion of execute-time `ParamForm` values to another type ignores
    whether the `ParamForm` value is `bound`.

### Form interfaces

Previously, interfaces had an implicit `Self` type parameter, set to the type
that is implementing the interface. We add the capability to explicitly declare
the `Self` parameter with a form type as a deduced parameter in square brackets
`[`...`]`:

```carbon
interface Callback[Self:! ParamForm] {
  fn Go[self:? Self]();
}

interface DefaultConstructible
    [Self:! ReturnForm] {
  fn MakeDefault() ->? Self;
}
```

`Callback` and `DefaultConstructible` are _form interfaces_, specifically a
`ParamForm` and a `ReturnFrom` interface respectively. A value of a form
interface is a _form facet_. These work the same way as ordinary "type"
interfaces except they use the matching kind of form values instead of type
values.

Let's break down what happens with an ordinary "type" interface:

```carbon
// Equivalent to: interface I[Self:! type]
interface I {
  fn F[self: Self]();
}

// Since `I` is effectively declared `I[Self:! type]`, that means
// `T` is a facet of a type, which means a type that is known to
// implement `I`. Since T is a facet of a type, it has an implicit
// conversion to type, so it can be used to the right of a `:` to
// give a type to `x`.
fn A[T:! I](x: T) {
  x.F():
  // - Looks in the type of `x` for a `F`
  // - Type of `x` is `T` is symbolic, so look in its type instead
  // - Type of `T` is `I`, has a member `F`, namely `I.F`
  // - Now evaluate `x.(I.F)`
  //   - `I.F` has signature `I[Self:! type].fn F[self: Self]()`
  // - Requires that the type of `x` implements `I`
  // - Satisfied by the bindings `x: T` and `T:! I`
}
```

Now look at how this works analogously with the `ParamForm` interface
`Callback`:

```carbon
// Since `Callback` is declared `Callback[Self:! ParamForm]`, that
// means `CF` is a facet of a `ParamForm`, which means a
// `ParamForm` that is know to implement `Callback`. Since `CF` is
// a facet of a `ParamForm`, it has an implicit conversion to
// `ParamForm`, so it can be used to the right of a `:?` to give a
// form to `c`.
fn InvokeCallback[CF:! Callback](c:? CF) {
  c.Go();
  // - Looks in the form of `c` for `Go`
  //   - If the form is a paren form, allow `.0`, `.1` access
  //   - If the form is a curly brace form, allow `.x`, `.c` access
  //   - If the form is atomic, look in its type (as above)
  //   - Since the form `CF` is symbolic, instead we look at `CF`'s type.
  // - Type of `CF` is `Callback`, has a member `Go`, namely `Callback.Go`
  // - Now evaluate `c.(Callback.Go)`
  //   - `Callback.Go` has signature
  //     `Callback[Self:! ParamForm].fn Go[self:? Self]()`
  // - Requires the *form* of `c` to implement `Callback`
  // - Satisfied by the bindings `c:? CF` and `CF:! Callback`.
}
```

Implementing a form interface and other operations also work analogously, using
form values instead of type values.

```
class V {}
// `ParamForm` values implement `Callback`,
// instead of type values, since `Callback`
// is a `ParamForm` interface (and a
// `ParamForm` facet type).
impl form(_: V) as Callback {
  // Notice the form of the `self` parameter
  // is `form(_: V)`, the value of `Self`.
  fn Go[self: V]() {
    Core.Print("Printed!");
  }
}

let v: V = {};
// The form of the expression `v` is
// `form(-> let V)`, which gets converted
// to the `ParamForm` `form(_: V)`. This
// `ParamForm` value implements `Callback`
// so this call typechecks with `CF`
// deduced to be `form(_: V) as Callback`.
//
// The `c.Go()` call in `InvokeCallback`
// prints "Printed!".
InvokeCallback(v);
```

With a form interface, we can change other aspect of the form beyond the type.
Here we show a similar example except with a `ref` `ParamForm`:

```carbon
class R {
  var m: i32;
}
impl form(ref _: R) as Callback {
  // Notice the form of the `self` parameter
  // is `form(ref _: R)`, the value of `Self`.
  fn Go[ref self: R]() {
    self.m += 2;
  }
}
var r: R = {.m = 3};
// This time `r` is a reference expression
// so `CF` is deduced to be
// `form(ref _: R) as Callback`.
InvokeCallback(r);
Assert(r.m == 5);
```

Finally, here is an example using a `ReturnForm` interface instead of a
`ParamForm` interface:

```carbon
// Init return form
impl form(-> R) as DefaultConstructible {
  fn MakeDefault() -> R {
    return {.m = 7};
  }
}
r = (form(-> R) as DefaultConstructible)
      .MakeDefault();
Assert(r.m == 7);

var global: R = {.m = 6};
// `ref` return form
impl form(-> ref R) as DefaultConstructible {
  fn MakeDefault() -> ref R {
    return global;
  }
}
(form(-> ref R) as DefaultConstructible)
      .MakeDefault().m += 3;
Assert(global.m == 9);
```

Combining this with variadics allows us to represent a more general version of
the `Call` interface that allows specifying forms:

```carbon
package Core;

interface CallPrimitive[Self:! ParamType](
    ... each Param:! ParamType) {
  let ResultForm:! ReturnForm;
  fn Op[self:? Self]
      (... each args:? each Param)
      ->? ResultForm;
}
```

This is cumbersome to write, though, so we introduce a `call(`...`)` convenience
syntax for writing a facet type of the `Core.CallPrimitive` interface.

| `call` syntax           | `ParamForm` facet type value                   |
| :---------------------- | :--------------------------------------------- |
| `call()`                | `CallPrimitive()`                              |
| `call(_: i32)`          | `CallPrimitive(form(_: i32))`                  |
| `call(_: i32, _: bool)` | `CallPrimitive(form(_: i32), form(_: bool))`   |
| `call(var _: bool)`     | `CallPrimitive(form(_: bool))`                 |
| `call(bound _: i32*)`   | `CallPrimitive(form(bound _: i32*))`           |
| `call(_:? X)`           | `CallPrimitive(X)`                             |
| `call() -> i32`         | `CallPrimitive() where .Result = form(-> i32)` |
| `call() -> ()`          | `CallPrimitive() where .Result = form(-> ())`  |

Note: If "`->` _\<return-type\>_" is not included at the end, the return type is
unconstrained. Use `-> ()` to mean "returns nothing."

### Compile-time parameter equal to a specified value

```

// ❌ not a different type

  // ❌ not known to be `i32`
```

### Deduction of aspects

FIXME

When a `BindingType` or `BindingAspect` value is deduced, as in:

```
fn F[B:! BindingType](x:? B);
fn G[P:! ParameterAspect(i32)](i:? (i32, P));
```

The aspect is deduced to match the phase and category of the argument supplied:

-   A compile-time argument will deduce a `CompileTimeEqual(V)`, including for
    symbolic constants.
-   An initializing expression argument will deduce a `VarAspect`.
-   A reference expression argument will deduce a `RefAspect`

Example:

```
let l: i32 = 3;

// Deduces `B` in `F` to be `(i32, ValueAspect)`.
F(l);

// Deduces `P` in `G` to be `ValueAspect`.
G(l);

var v: i32 = 2;

// Deduces `B` in `F` to be `(i32, RefAspect)`.
F(v);

// Deduces `P` in `G` to be `RefAspect`.
G(v);

// A call to `Make()` is an initializing expression.
fn Make() -> i32;

// Deduces `B` in `F` to be `(i32, VarAspect)`.
F(Make());

// Deduces `P` in `G` to be `VarAspect`.
G(Make());

// Deduces `B` in `F` to be `(i32, CompileTimeEqual(4 as i32))`.
F(4 as i32);

// Deduces `P` in `G` to be `CompileTimeEqual(4 as i32)`.
G(4 as i32);

fn H(N:! i32) {
  // Deduces `B` in `F` to be `(i32, CompileTimeEqual(N))`.
  F(N);

  // Deduces `P` in `G` to be `CompileTimeEqual(N)`.
  G(N);
}
```

### Callables that may or may not mutate

FIXME

In many cases, a function accepting a callable object will not care about
whether the call mutates the object.

```
fn CallbackNoMutation() -> i32 {
  // https://xkcd.com/221/
  return 4;
}

class Counter {
  var count: i32;
  impl as call() -> i32 fn [self: Self]() -> i32 {
    self.count += 1;
    return self.count;
  }
}
var counter: Counter = {.count = 0};
```

There are two approaches to accommodating this that are supported by the current
design. The function taking the callable object can be generic on its aspect in
the caller, as in:

```
fn GenericCaller
    [PF:! Core.CallPrimitive() where .Result = i32]
    (f:? PF) -> i32 {
  return f();
}

Assert(GenericCaller(CallbackNoMutation) == 4);
Assert(GenericCaller(counter) == 1);
```

Alternatively, we can have the function takes its argument by value, and make a
wrapper that holds a pointer to make the call:

```
// Only has to be defined once
class CalledThroughPointer(T:! type) {
  var p: T*;
}

fn CallThroughPointer[T:! type](p: T*)
    -> CalledThroughPointer(T) {
  return {.p = p};
}

impl forall
    [... each P:! ParamForm,
    // FIXME: Need to go from a form facet type
    // to a facet type by restricting to
    // Self = form(ref _: T).
     T:! Core.CallPrimitive(... each P)]
    form(_: CalledThroughPointer(T)) as
    Core.CallPrimitive(... each P) {
  where Result = T.Result;
  fn [self: Self](... each param:? each P) -> Result {
    return (*self.p)(... each param);
  }
}

fn ValueCaller[FNT:! call() -> i32](f: FNT) -> i32 {
  return f();
}

Assert(ValueCaller(CallbackNoMutation) == 4);
Assert(ValueCaller(CallThroughPointer(&counter)) == 1);
```

This is more convenient when defining the function (`ValueCaller`), but less
convenient when calling it (since you have to add `CallThroughPointer(&...)`).
On the other hand, this does have the benefit of highlighting that the callable
object may be mutated.

### `ref?`

We would like to support being generic across `let` and `ref` for accessor
functions -- where the `self` and the return are both `let` or both `ref`. issue
is we can do input-to-input, output-to-output, and output-to-input forwarding of
all three categories, but accessors want to do input-to-output forwarding which
we can't do for initializing expressions. Do we want a special syntax for just
this case like `ref?`, as in:

```carbon
class C {
  private var x: D;
  fn AccessX[ref? self: Self]() -> ref? D {
    return self.x;
  }
}
```

This would be equivalent to an overload of the two versions of the function.
`ref?` would have to be used on at least one explicit or `self` parameter, and
the `ref` version would be used if all of those arguments were reference
expressions. An initializing expression counts as a `let` expression for those
purposes, since `ref` would mean enabling mutation of a temporary. Is it a flaw
in the design that `ref?` looks to be a useful form genericity, but is not well
supported without a separate feature? Want something like:

```carbon
fn AccessX[PF:! LetOrRef(Self), self:? PF]() ->? ReturnFormWithCategory(PF, D);
```

So we are missing `LetOrRef` (passed a type and returns a form facet type),
`ReturnFormWithCategory` (passed a `CommonForm` and a type, returns a return
form value), and the machinery to definition check this generically.

### Tuple patterns as parameters instead of tuple aspects

First we add supporting tuple pattern in the parameter list for functions.

```
fn Dist((x1: f32, y1: f32), (x2: f32, y2: f32)) -> f32 {
  var dx: f32 = x2 - x1;
  var dy: f32 = y2 - y1;
  return Math.Sqrt(dx * dx + dy * dy);
}
```

is equivalent to:

```
fn Dist(p1: (f32, f32), p2: (f32, f32)) -> f32 {
  var dx: f32 = p2.1 - p1.1;
  var dy: f32 = p2.2 - p1.2;
  return Math.Sqrt(dx * dx + dy * dy);
}
```

```
}

```

```
  return f(... each args1) + g(... each args2);
}
```

### Decoupling type from the rest of the form

The goal of this approach was to avoid introducing form interfaces. Instead, the
non-type parts of the form could passed in as a separate parameter to supplement
the `Self` type. This ran into a few problems though:

-   It didn't support compound forms well, and as a result had trouble
    supporting some forwarding use cases.
-   For the compile-time value form `form(N)`, the additional information beyond
    the type includes a value of that type. As a result, the additional
    information was parameterized by the type, which was complex and introduced
    dependency cycles in some cases.
