## Abstract

We propose:

-   A syntax for a compile-time parameter that is equal to a specified value.
-   Special types `ParamBindingType` and `ParamAspect` that can be used to
    customize parameters in the signature of member functions. Impl lookup will
    allow some conversions between `ParamBindingType` values in interface
    arguments.
-   Use these special types to add support for different parameter categories
    and compile-time parameters to the `Core.Call` call operator interface.
-   A `call(...)` syntax for writing a specific of the `Core.Call` interface.

## Problem

The `Core.Call` interface defined in
[proposal #2875](https://github.com/carbon-language/carbon-lang/pull/2875) does
not support all of the features of function calls:

-   `var` parameters.
-   Mutation of the callable object using `addr self`.
-   Compile-time parameters, as designated by `:!` or `template`...`:!`.
-   Compile-time parameters that are mentioned elsewhere in the signature

In addition, we want to be able to express these aspects of parameters in other
contexts:

-   Some interfaces, such as operators, should support impls specifying these
    aspects for the parameters of the interface's member functions. For example,
    a type should be able to implement `Core.AddWith` in a way that uses `var`
    or compile-time parameters.
-   We would like there to be a way to forward arguments passed to one function
    to another function it calls, preserving those aspects. For example, there
    should be a way to write
    [`Apply`](https://en.wikipedia.org/wiki/Function_application) that takes a
    function and arguments to call it with and performs the call (so
    `Apply(F, x)` returns `F(x)`).

FIXME: A syntax for a compile-time parameter that is equal to a specified value.

```
// Argument must be a compile-time value equal to `i32`
fn F(==! i32);

// ✅ Allowed
F(i32);

// ❌ not something with type `i32`
F(7 as i32);

// ❌ not a different type
F(i16);

fn G(T:! type) {
  // ❌ not known to be `i32`
  F(T);
}

fn H(template T:! type) {
  F(T);
}

// ✅ Allowed
H(i32);

// ❌ error substituting in `i16` for `T`
H(i16);
```

This provides a resolution of
[Leads issue #578](https://github.com/carbon-language/carbon-lang/issues/578),
giving a method to work around ordering constraints on parameters:

```
fn DoACast[U:! type, T:! ImplicitAs(U)]
    (x: T, ==! U) -> U {
  return x as U;
}

DoACast(7, i32);
```

It is also needed by this proposal to model explicit generic parameters, so they
can be used in other parts of the signature.

FIXME: "aspect" terminology to encompass the category and phase of a binding.

FIXME: the special type `ParamBindingType`:

-   Values are compile-time only, like types.
-   Type and facet values implicitly convert to `ParamBindingType`.
-   A tuple `(T, A)` where `T:! type` and `A:! ParamAspect(T)` implicitly
    converts to `ParamBindingType`.
-   Values can be used to customize parameters in the signature of member
    functions, using a new `:?` binding syntax.
-   Impl lookup will allow some conversions between `ParamBindingType` values in
    interface arguments. Specifically these conversions match what is allowed
    when passing arguments to a function. For example, a value binding of type
    `T` could be converted to a `var` binding for a type `T` if `T` is copyable.
-   A `ParamBindingType` value is deducible from an argument, allowing it to
    capture the argument's category and phase.

Names of aspect values:

| example binding  | aspect name                               |
| :--------------- | :---------------------------------------- |
| `_: T`           | `ValueAspect` / `ValueCategory`           |
| `var _: T`       | `VarAspect` / `VarCategory`               |
| `ref _: T`       | `RefAspect` / `RefCategory` (after #5261) |
| `_:! T`          | `CompileTimeAspect` / `CompileTimePhase`  |
| `template _:! T` | `CompileTimeAspect` / `CompileTimePhase`  |
| `==! V`          | `CompileTimeEqual(V)`                     |
| `_: (...)`       | `TupleAspect(...)`                        |

### Deduced parameters

FIXME: Not modeled as part of the interface, but using parameterized `impl`s.

```carbon
fn F[T:! type](x: T) -> T;
```

can be modeled as

```carbon
class __F_Type {}
let F:! __F_Type = {};
impl forall [T:! type] __F_Type as Call(ValueAspect, T) where .Result = T;
```

or equivalently:

```carbon
class __F_Type {}
let F:! __F_Type = {};
impl forall [T:! type] __F_Type as call(_: T) -> T;
```

### Explicit compile-time parameters

FIXME

```carbon
fn F(T:! type, x: T) -> T;
```

can be modeled as:

```carbon
class __F_Type {}
let F:! __F_Type = {};
impl forall [T:! type] __F_Type as
    Call(ValueAspect,
         (type, CompileTimeEqual(T)),
         T)
    where .Result = T;
```

or equivalently:

```carbon
class __F_Type {}
let F:! __F_Type = {};
impl forall [T:! type] __F_Type as call(==! T, _: T) -> T;
```

### Deduction of aspects

FIXME

When a `ParamBindingType` or `ParamAspect` value is deduced, as in:

```
fn F[B:! ParamBindingType](x:? B);
fn G[P:! ParameterAspect(i32)](i:? (i32, P));
```

The aspect is deduced to match the phase and category of the argument supplied:

-   A compile-time argument will deduce a `CompileTimeEqual(V)`, including for
    symbolic constants.
-   An initializing expression argument will deduce a `VarAspect`.
-   A reference expression argument will deduce a `RefAspect`

Example:

```
let l: i32 = 3;

// Deduces `B` in `F` to be `(i32, ValueAspect)`.
F(l);

// Deduces `P` in `G` to be `ValueAspect`.
G(l);

var v: i32 = 2;

// Deduces `B` in `F` to be `(i32, RefAspect)`.
F(v);

// Deduces `P` in `G` to be `RefAspect`.
G(v);

// A call to `Make()` is an initializing expression.
fn Make() -> i32;

// Deduces `B` in `F` to be `(i32, VarAspect)`.
F(Make());

// Deduces `P` in `G` to be `VarAspect`.
G(Make());

// Deduces `B` in `F` to be `(i32, CompileTimeEqual(4 as i32))`.
F(4 as i32);

// Deduces `P` in `G` to be `CompileTimeEqual(4 as i32)`.
G(4 as i32);

fn H(N:! i32) {
  // Deduces `B` in `F` to be `(i32, CompileTimeEqual(N))`.
  F(N);

  // Deduces `P` in `G` to be `CompileTimeEqual(N)`.
  G(N);
}
```

### Tuple patterns as parameters instead of tuple aspects

FIXME: Old text:

First we add supporting tuple pattern in the parameter list for functions.

```
fn Dist((x1: f32, y1: f32), (x2: f32, y2: f32)) -> f32 {
  var dx: f32 = x2 - x1;
  var dy: f32 = y2 - y1;
  return Math.Sqrt(dx * dx + dy * dy);
}
```

is equivalent to:

```
fn Dist(p1: (f32, f32), p2: (f32, f32)) -> f32 {
  var dx: f32 = p2.1 - p1.1;
  var dy: f32 = p2.2 - p1.2;
  return Math.Sqrt(dx * dx + dy * dy);
}
```

This allows us to support multiple variadic parameters by delimiting them with
parentheses:

```
fn Log[... each T:! As(String)]
    (msg: String, (... each args: each T),
    (... each sink: LogSink)) {
  var result: String = FormatString(msg, ... each args);
  ... each sink.Send(result);
}

Log("Format string {0} and {1}", (3, true), (log_sink1, log_sink2));
```

And in particular, this approach allows us to do the same while capturing the
aspects of the arguments:

```
fn CallBoth[... each T1:! ParamBindingType,
            FNT1:! Call(ValueAspect, ... each T1) where result = i32,
            ... each T2:! ParamBindingType,
            FNT2:! Call(ValueAspect, ... each T2) where result = i32]
    (f: FNT1, (... args1:? each T1),
     g: FNT2, (... args2:? each T2)) -> i32 {
  return f(... each args1) + g(... each args2);
}

fn F(x: i32, y: i32) -> i32;
fn G(x: bool, y: bool) -> i32;

var result: i32 = CallBoth(F, (1, 2), G, (true, false));
```

or using the `call` syntax

```
fn CallBoth[... each T1:! ParamBindingType,
            FNT1:! call(... _:? each T1) -> i32,
            ... each T2:! ParamBindingType,
            FNT2:! call(... _:? each T2) -> i32]
    (f: FNT1, (... args1:? each T1),
     g: FNT2, (... args2:? each T2)) -> i32 {
  return f(... each args1) + g(... each args2);
}

fn F(x: i32, y: i32) -> i32;
fn G(x: bool, y: bool) -> i32;

var result: i32 = CallBoth(F, (1, 2), G, (true, false));
```
