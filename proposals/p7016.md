## Abstract

Update the syntax for class (and interface/`impl`) methods to move `self` into
the parameter parentheses `()` and make its type binding optional (defaulting to
`Self`). Introduce the `static` keyword for non-instance fields to indicate
static storage. Reflects the decision in leads issue
[#6931](https://github.com/carbon-language/carbon-lang/issues/6931).

## Problem

Carbon's syntax for defining instance methods and non-instance members (static
members in C++ terminology) needs refinement to balance ergonomics, clarity, and
consistency across classes, interfaces, and `impl` blocks.

The current syntax for method definitions can be heavy, and there is no clear
way to declare non-instance fields (class variables) that works uniformly across
all contexts (classes, interfaces, `impl`s).

## Background

Leads discussed various syntax tweaks for class members in issue
[#6931](https://github.com/carbon-language/carbon-lang/issues/6931). The
discussions focused on find a design that scale from simple classes to complex
interface implementations.

Key tension points included:

-   Where to place `self` (in `[]` versus `()`).
-   How to distinguish instance methods from non-instance functions.
-   How to declare non-instance fields without overloading keywords or creating
    confusion in interfaces vs classes.

## Proposal

We propose the following updates to the syntax for class members:

1.  **Move `self` to the `()` parameter list**: Instance methods declare `self`
    as the first parameter in the standard parameter parentheses. This aligns
    methods with the **partial-application model** (see Rationale).
2.  **Make `self` type optional**: Omit `: Self` to default to the enclosing
    type (for example, `fn F(self)`).
3.  **Use `static` for non-instance fields**: Use `static var` for data members
    tied to the type rather than instances.
4.  **No keyword for non-instance methods**: Functions without a `self`
    parameter are automatically non-instance functions.

As a consequence of this model, methods are fundamentally functions and can be
called using standard function call syntax (for example, `MyClass.Method(obj)`),
not just method call syntax (`obj.Method()`). This makes method calls
essentially perform partial application.

However, we retain the current model for the meaning of `obj.Method` -- it is a
"bound member function" that adapts `obj`. This is important as we don't know
how to convert `obj` to the `self` parameter of `Method` until we actually try
to call it with an argument list. Similarly, we expect
`obj.(Class.Method)(args)` to follow the same model, and `obj.(Class.Method)` to
form a callable bound method adapter. For a given constant expression of a
method `M`, we expect `x.(M)` means `x as BoundMethod(TypeOf(x), M)`, and given
`b: BoundMethod(T, M)`, `b(args)` means `M(x as T, args)` where `x` is the bound
object.

## Details

### Member functions

We suggest moving away from the terminology "class function" as it ends up being
confusing when used in contexts like an interface or where "class" is already
being used differently. Instead, we consider all functions declared within a
class, interface, or impl to be _member functions_.

Non-instance member functions don't use any special syntax. They don't take a
`self` parameter and so are regular functions. For example:

```carbon
class Point {
  var x: i32;
  var y: i32;

  // No `self` parameter, so it's a regular, non-instance function.
  fn Create() -> Self {
    return {.x = 0, .y = 0};
  }
}

fn F(p: Point) {
  var p2: Point = Point.Create();
}
```

Instance member functions, or _methods_, declare `self` as the first parameter
in the `()` list. The type binding `: Self` is optional and defaults to
`: Self`.

```carbon
class Point {
  var x: i32;
  var y: i32;

  // Explicit type binding.
  fn GetX(self: Point) -> i32 { return self.x; }

  // Omitted type binding (defaults to Point).
  fn GetY(self) -> i32 { return self.y; }

  // By-reference binding.
  fn SetX(ref self, new_x: i32) { self.x = new_x; }
}
```

#### Calling without method syntax

Because methods are modeled as functions with an explicit `self` parameter, they
can be called directly by way of the type name without using dot-notation:

```carbon
fn F(p: Point) {
  // Standard method call syntax:
  var x1: i32 = p.GetX();

  // Non-method call syntax (partial-application style):
  var x2: i32 = Point.GetX(p);
}
```

### Member variables

_Member variables_ are any `var`s declared within a class context (or in the
future, potentially an interface or `impl` context).

Instance member variables, or _fields_, are unchanged in the current design.

This proposal adds support for non-instance member variables, or _static member
variables_, using the `static` modifier keyword on the `var` declaration. Static
member variables are associated with the type itself rather than instances of
the type, and have static storage duration.

```carbon
class Widget {
  // Non-instance field.
  static var count: i32;

  // Non-instance function.
  fn ResetCount() { count = 0; }
}
```

This syntax should apply uniformly to classes, and in the future if we add
associated fields, interfaces, and `impl` blocks.

## Rationale

This proposal effectively advances Carbon's goals by focusing on:

-   [Code that is easy to read, understand, and write](/docs/project/goals.md#code-that-is-easy-to-read-understand-and-write):
    Moving `self` to the "normal" parameter list better matches the semantics of
    the object argument and the partial-application model. Making the `: Self`
    part optional reduces clutter in the most common cases and matches the
    syntax used in other languages like Rust.
-   [Software and language evolution](/docs/project/goals.md#software-and-language-evolution):
    Focusing `static` on storage (fields) provides a crisp definition that works
    unambiguously across classes, interfaces, and `impl` blocks.

### Unification and Partial-Application Model

Moving `self` into the parentheses reinforces the conceptual model that method
calls are sugar for function calls with an explicit object argument.
Specifically, `obj.Method(args...)` is equivalent to
`Type.Method(obj, args...)`.

This **partial-application model** unifies methods and functions: there is only
one kind of function definition. A function is an "instance method" if and only
if its first parameter is named `self`.

This avoids alternative more complex models such as:

-   **Receiver Model**: Where the object is a "magical" entity outside the type
    system or parameter list (for example, C++ `this`).
-   **Bound-Member Model**: Where `obj.Method` would form a "closure" or "fat
    pointer" object. Carbon avoids the complexity of bound-member types by
    treating method access as a direct function call with the object applied.

This unification simplifies generic programming and C++ interoperability, as it
minimizes special exceptions for member functions.

The decision to use `static` for fields and _no keyword_ for non-instance
methods leans on the distinction between storage and behavior. `static` implies
storage lifetime, which fits data fields well. For functions, the absence of a
`self` parameter is sufficient to distinguish them from methods without
stretching the meaning of `static`. This distinction aligns with common
definitions of [static variables](https://en.wikipedia.org/wiki/Static_variable)
focusing on lifetime contrasted with scope.

## Alternatives considered

### `class` modifier for non-instance members

Instead of `static var`, using `class var` or `class fn` was considered.
**Rejection rationale:** `class` is already an introducer in Carbon. Using it as
a modifier adds an overloaded meaning. This meaning would also diverge from
usage in other languages. For example, Swift uses `class` versus `static` to
distinguish between class and struct methods, and has complex virtual dispatch
rules that aren't part of the Carbon design. These members also appear in
interfaces and `impl` blocks where the `class` keyword would be mildly
surprising.

### `shared` or `global` keywords for non-instance fields

Alternatives to `static` like `shared var` or `global var` were considered to
avoid C++'s overloaded usage of `static`. **Rejection rationale:**

-   **`shared`**: This term is heavily associated with concurrency and thread
    safety (for example, shared ownership, shared pointers). Reserving it for
    class membership would collide with its use for future concurrency features
    (see
    [concurrency control design](https://docs.google.com/document/d/1WVWcmJdVBlapza_kPj2l3mOO-yw_hNXpb2u-Ren-I5M/)
    and
    [shared memory in CUDA](https://developer.nvidia.com/blog/using-shared-memory-cuda-cc/)).

    Some of these might be related and even highly compatible overlap, and in
    common cases it would provide a certain amount of semantic connection -- for
    example these variables are very likely to be shared between threads.

    On the other hand, there would be interesting cases where we would do
    something _other_ than mark something as `shared`, but still end up sharing
    it between threads and potentially referring to its place set as `shared`.

    Overall, the risk of confusion outweighed the symmetry benefits where the
    meanings matched.

-   **`global`**: Most widely used to refer to _scope_ (global scope), whereas
    these members are explicitly scoped to a type, or potentially in the future
    an interface. See for example the start of the two Wikipedia articles on
    [Static variable](https://en.wikipedia.org/wiki/Static_variable) vs
    [Global variable](https://en.wikipedia.org/wiki/Global_variable). The most
    common distinction is that of "global" implicating _scope_ or _access_,
    while "static" more consistently means the _storage_ which is how we are
    using it.

### `static` for non-instance class functions as well as non-instance fields

Applying `static` to both `static var x: i32;` and `static fn F();` for
consistency with C++, C#, and Swift (see
[Type Methods](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/methods#Type-Methods)).
**Rejection rationale:** The leads preferred to tie `static` strictly to
**storage duration** (lifetime). Non-instance data members have storage and a
storage duration of the entire program execution, which fits the definition of a
[static variable](https://en.wikipedia.org/wiki/Static_variable). Functions do
not have "storage", and so using the keyword for them would weaken this
interpretation.

### Distinct `method` introducer

Using `method F()` instead of `fn F(self)`. **Rejection rationale:** The leads
currently prefer a uniform `fn` introducer for all functions, relying on the
presence of the `self` parameter to identify methods. This provides greater
consistency across all different kinds of functions, including even lambdas.

### Special `self` syntax in square brackets `[]`

Placing `self` in square brackets (for example, `fn F[self: Self](...)`) was
considered as it visually distinguished the object parameter from other
parameters and has been the historical syntax in Carbon.

**Rejection rationale:** We expect users to strongly associate square brackets
with compile-time parameters, as those are the typically "deduced" parameters to
functions. While we may add implicit runtime parameters in the future, even then
they would be significantly more rare than compile-time parameters. Using `self`
in the same context loses that consistency. For example, if we pursue
context-based distinguishing of compile-time versus runtime parameters as
suggested in
[issue #6932](https://github.com/carbon-language/carbon-lang/issues/6932), then
`self` would have to trigger an exception to the contextual rule.

There was also a general appreciation for the consistency of putting `self` in
the `()`s because there are many different ways in which its behavior matches
what we expect for "normal" parameters:

-   The object argument may be implicitly converted to match the type declared
    for the `self` parameter, just like any other arguments.
-   Lifetime and other semantics match that of arguments as they are tied to the
    call expression.

Fundamentally, the leads see two workable models for how methods work in Carbon
-- one of partial application of the object argument, and one of a truly special
and bespoke kind of parameter. The semantics we currently have match the first
of these well, and so it seems natural to embrace that model rather than having
`self` in a different position.
