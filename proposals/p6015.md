## Abstract

To avoid ambiguity in the grammar, this proposal disallows arbitrary patterns
when declaring a namespace qualified name.

## Problem

The current documentation allows for pattern matching for namespace global
variable declarations as long as the variables are all in the same namespace.
However, this may still be problematic as the first qualifier would presumably
change the scope in which any later qualifiers are parsed.

## Background

It was also decided to disallow arbitrary patterns when declaring a field in a
class scope and when declaring an associated constant in an interface scope.
[PR 5320](https://github.com/carbon-language/carbon-lang/pull/5320) and
[PR 5973](https://github.com/carbon-language/carbon-lang/pull/5973) implemented
these respective cases already.

## Proposal

`let` and `var` will either have an arbitrary pattern without namespace
qualifiers or a single namespace qualified name with the following grammar:

```
[let|var] [QUALIFIER] NAME : TYPE [= INIT];
```

## Rationale

### [Software and language evolution](/docs/project/goals.md#software-and-language-evolution)

This is a starting position to allow for declaring namespace variables that
gives enough flexibility to explore useful idioms. It still allows for
initializing namespace globals from a single function, and can be extended to
allow a one-liner in the future.

```
// instead of this...
let (A.x: i32, {.b = B.y: i32, .c = C.z: i32}) = F();

// ...write this:
private let (x: i32, {.b = y: i32, .c = z: i32}) = F();
let A.x: i32 = package.x;
let B.y: i32 = package.y;
let C.z: i32 = package.z;
```

### [Code that is easy to read, understand, and write](/docs/project/goals.md#code-that-is-easy-to-read-understand-and-write)

The functionality and behaviour of this proposal is straightforward to explain
and does not introduce any new syntax.
